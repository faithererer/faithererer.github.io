## redis的五种数据类型
### String
存储常见的数据
Redis 并没有使用 C 的字符串表示，而是自己构建了一种 **简单动态字符串**（Simple Dynamic String，**SDS**）。相比于 C 的原生字符串，Redis 的 SDS 不光可以保存文本数据还可以保存二进制数据，并且获取字符串长度复杂度为 O(1)
应用场景：
- 计数
- 普通数据如缓存 Session、Token、图片地址、序列化后的对象
- 分布式锁setnx
### list
Redis 的 List 的实现为一个 **双向链表**，即可以支持反向查找和遍历，更方便操作，不过带来了部分额外的内存开销。
场景:
- 举例：最新文章、最新动态。
- 相关命令：`LPUSH`、`LRANGE`。
### Hash
Hash 类似于 JDK1.8 前的 `HashMap`，内部实现也差不多(数组 + 链表)。不过，Redis 的 Hash 做了更多优化。
应用场景：
- 对象数据存储场景
### set
- Redis 中的 Set 类型是一种无序集合，集合中的元素没有先后顺序但都唯一，有点类似于 Java 中的 `HashSet` 。当你需要存储一个列表数据，又不希望出现重复数据时，Set 是一个很好的选择，并且 Set 提供了判断某个元素是否在一个 Set 集合内的重要接口，这个也是 List 所不能提供的。
应用:
- 需要获取多个数据源交集、并集和差集的场景,共同好友(交集)、共同粉丝(交集)、共同关注(交集)、好友推荐（差集）、音乐推荐（差集）、订阅号推荐（差集+交集） 等场景。
- 需要随机获取数据源中的元素的场景，适合不允许重复中奖的场景

### sortset
Sorted Set 增加了一个权重参数 `score`，使得集合中的元素能够按 `score` 进行有序排列，还可以通过 `score` 的范围来获取元素的列表。有点像是 Java 中 `HashMap` 和 `TreeSet` 的结合体。
应用;
- 需要随机获取数据源中的元素根据某个权重进行排序的场景,比如微信步数，礼物排行榜

## 缓存更新策略有哪几种，有什么优缺点，你的策略是什么
### 缓存更新策略有哪几种，有什么优缺点
分为主动更新和被动更新
#### 被动更新
- 内存淘汰策略
不同自已维护，利用Redis的内存清除机制，一旦内存不足时自动淘汰部分数据，下次查询缓存
- 超时剔除
给数据设置过期时间，过期失效后，查询数据库回写缓存

#### 主动更新
分为三种
- Cache Aside 旁路缓存
更新缓存时，同时更新，由调用者来调用
- Read/write Through Patter写穿读穿策略
只操作缓存，db缓存整体，无此服务
- Write Behind Caching Pattern写回策略
只操作缓存，可能丢失数据

### 你的策略
使用旁路缓存
- 查询策略：缓存存在直接返回，不存在查询数据库，回写缓存
- 更新策略：先操作数据库再操作缓存。
#### 为什么先操作数据库再操作缓存
主要数据的一致性考虑，该方案数据一致性较高。
如果先操作缓存再操作数据库，假设有读写线程，写线程需要更新数据，于是删除了缓存，正在更新数据库，此时，读线程读取了数据库的数据回写旧数据到缓存，而后写线程完成了新数据的操作，造成了缓存和数据库的不一致的局面。
#### 当前方案就没有不会造数据一致性问题吗
也会造成，只不过概率远远低于前者。
假设读写线程，缓存已经失效，读线程读数据库，回写缓存，在这个过程中，写线程进行了数据库更新并且删除缓存，删了个寂寞，而后读线程回写了旧值，造成了数据不一致问题。
#### 为什么删除缓存，而不是更新缓存
无效写多，加入更新耗费算力，下一次查询期间进行了大量更新，都是无效更新。

## 你如何解决超卖问题的
超卖问题就是使用在高并发的场景下，销售量超出库存的情况，主要问题是并发控制的问题。
采用一个自己实现的分布式锁

某一商品被多个线程访问，假设5个线程读了相同的值,都进行了减库存策略，理应库存为x-5，实际上是x-1。

解决方法是个商品添加互斥锁,锁的是库存key，只有获得锁的线程可以进行减库存操作，互斥锁应该是分布式的，便于分布式场景下的获取的是同一把锁。利用redis的setnx。使用分布式锁性能太差，采取**乐观锁**，利用库存作为版本号，当库存>0时支持操作。


### 一人一单是什么问题

一人一单就是一个人使用非正常手段，对同一优惠券发起大量请求，造成一人多单的情况

多个线程，同时判断用户是否存在，此时多个线程都读到不存在，然后创建了多个订单。

## 怎么解决一人一单
使用分布式锁，针对用户id加锁。(不同用户不会锁住)
锁存储uuid+thread，防止key过期时，锁误删


### 什么情况下会锁误删
因为锁都是有有效期的吗，不然可能有锁泄露问题。
假设多线程访问，a线程获得了锁,锁了userId,然后执行业务时间较长，释放了，b线程之后获取了锁，在b线程执行途中，a线程执行完了，删除了b的锁,此时c 线程来了，造成了并发。

使用uuid+thread可以解决加锁的特定线程标识，只有他才可以释放锁。

### 锁不续期，有什么问题
线程执行过程时间长，锁过期，另一个线程趁虚而入，并发。

使用线程池，进行锁续期。

基于Java语言实现的单数据库，支持常见的DML和DDL，采用C/S架构，支持多客户端通过Socket连接到服务器，执行SQL语句返回结果。将整个系统分层解耦，分为事务管理，数据存储，版本管理，索引构建，表格管理，解析器，连接器7个模块。

事务管理： 定义事务的三种状态： active，committed，aborted，通过XID 格式的文件进行持久化存储。定义并实现了事务的基本动作，包括开始事务，提交事务，回滚事务等等。
    
数据存储： 作为上层模块和文件系统之间的一个抽象层，向下直接读写数据库和日志文件，向上提供数据的包装DataItem。使用缓存机制，引用页面索引的分配机制来提高查询效率，以8KB大小的数据页为基本读取单位，采用引用计数的内存淘汰策略。提供数据恢复机制，通过日志文件实现，解决宕机等问题造成的数据不完整性。
    
版本管理： 基于两段锁协议实现了调度序列的可串行化，并实现了 MVCC 以消除读写阻塞。同时实现了RC和RR两种隔离级别。
    
索引构建： 采用B+Tree数据结构，使系统在大规模数据下仍保持低次数的磁盘IO，提高查询效率。
    
表格管理: 负责表和字段的信息管理，将表，字段，记录的二进制信息抽象为Java对象，表之间采用链表串联，使用头插法。
    
解析器： 解析SQL语句，词法分析为一个个Token，根据Token进行语法和语义分析，调用下层模块执行SQL操作。

连接器： 服务端使用Socket与客户端进行通信，客户端有Java命令行程序和Web端两种实现。
